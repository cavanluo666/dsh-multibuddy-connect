补齐数据面与配置界面：3 个后端可真正发消息、9 个后端可在设置页配置

背景
之前只交付了「管理面」（账号识别/额度读取/模型名册）。这带来两个可见缺口：
设置页只能配置 WorkBuddy，以及 8 个合并后端根本不在模型选择器里 —— 因为
它们从未注册 provider，也没有传输层。

新增：可复用的 OpenAI 兼容传输层
src/backends/openai-compat.ts：把 createProvider + PiAiAdapter 的接线收敛成一处。
Cline / CodeBuddy / OpenCode 只差 baseUrl、key 与名册的来源，协议与 harness 接缝
完全相同；写三遍就等于三处在 pi-ai profile 新增必填字段时被遗漏。

新增：通用的 provider 发布
index.ts 按 descriptor.serves 静态门控，只为真正能发消息的后端解析账号并注册
LLM 路由。启动期不再扫描那 8 个无法服务的后端 —— 那会读别家应用的文件、有的还会
建网络会话，且实测会扰动既有的 catalog 测试。

新增：三个传输层
- Cline：OpenAI 兼容，key 逐请求从凭据注册表现取
- CodeBuddy：OpenAI 兼容，且实现了**内存令牌续期**（不回写桌面端文件，
  严格只读；刷新令牌轮换，因此缓存放在实例上并做并发单飞）
- OpenCode：baseUrl 与密码取自运行时端点文档

新增：多后端配置界面
- 宿主路由 /plugins/.../backends（GET 文档 / POST 写）与 /backends/action
  沿用 loopback + 进程内密钥；密钥只以掩码形式下发，永不回传原文
- 客户端 BackendsCard：一张卡片按后端分节。configurable 的后端（api-key）
  可增删账号；desktop-adoption 与 managed-runtime **不提供**添加账号控件，
  改为状态与指引 —— 按钮背后没东西比没有按钮更糟

顺带修掉的既有缺陷
@earendil-works/pi-ai 在本树装了两份、类型面不同，adapter.ts 的 piProvider 赋值
因此报错，**上游仓库的 typecheck 本来就是失败的**。在两处包边界各加一次带说明的
类型转换后，全仓库双端 typecheck 首次零错误。

测试 707 个全部通过（新增 26 个后端路由测试，覆盖注册契约、掩码不外泄、
拒绝为不可配置的后端写入、真实 HTTP 行为）。双端类型检查零错误。

已知限制（诚实记录）
- OpenCode：原生 server 用 Basic 认证且没有 /v1/chat/completions，
  本传输层依赖一个 Bearer 校验的 OpenAI 兼容回环代理；直连原生端点会 401/404
- CodeBuddy：聊天请求可能还需要 X-CodeBuddy-Request 等额外头，
  当前接口只能表达 Bearer，未验证真实网关
- Cline / OpenCode 的模型名册是注册时的快照，配置写入或重启后刷新
